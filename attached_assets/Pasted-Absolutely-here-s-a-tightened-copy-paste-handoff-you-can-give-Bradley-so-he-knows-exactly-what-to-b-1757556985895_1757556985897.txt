2) API surface (all JSON)

Mount point: app.use("/api/availability", availabilityRoutes) etc.

Public

GET /api/availability?from=ISO&to=ISO&hours=2|4|6

Resp: { slots: string[] } ISO datetimes (start times).


POST /api/appointments (already exists—do not remove)

Server adds: compute end = start + hours; final overlap check; save; send emails; generate reschedule token.


GET /api/reschedule/:token

Resp: { id, title, start, end, hours } or 404.


POST /api/reschedule/:token

Body: { startISO }

Enforce 12h minimum notice (configurable).

Recompute end, overlap check, update DB, bump sequence, send updated emails.



Admin (protected)

GET /api/admin/schedule → appointments + blocks

POST /api/admin/block → { reason, startISO, endISO, isFullDay? }

GET /api/availability/rules

POST /api/availability/rules → { weekday, startTime, endTime, active }

PUT /api/availability/rules/:id

DELETE /api/availability/rules/:id


Deliverable: routes, validation, error handling.

3) Availability engine (server util)

File: server/utils/availability.ts

Inputs: { from: Date, to: Date, blockMinutes: number, stepMinutes=30 }

Data sources: availability_rules, appointments(start..end), blocked_times(start..end)

Logic: build windows per day from rules → scan in 30-min steps → accept slot if [start, end) doesn’t overlap any busy interval and fits within window.

(Optional) add a 15–30 min buffer by inflating busy intervals.


Deliverable: exported getOpenSlots() used by /api/availability.

9) Acceptance tests (how we’ll verify)

1. Rules only: With M–F 9–5 and no busy events, /api/availability&hours=2 returns starts 09:00–15:00.


2. Block applied: Add block 12:00–13:00 → 12:00 and 12:30 disappear.


3. Booking: Book a 2h slot → appointment saved, 2 emails sent, ICS attached.


4. Conflict: Try to book same slot twice → second returns 409.


5. Reschedule: Move booked appt → emails re-sent, ICS updates (sequence+1), original time becomes free.


6. Cutoff: Try reschedule within 12h → 409 with friendly message.


7. No customer cancel: No cancel endpoint/link visible; admin can still cancel internally.
